# Skyline Stacker Constitution

Skyline Stacker is a 2.5D crane tower-stacking web game with a city-building meta-game.
`docs/PRD.md` is the source of truth for features, numbers, and phases. This constitution
defines the non-negotiable engineering principles that every spec, plan, and task MUST follow.
Section references (§) point to `docs/PRD.md`.

## Core Principles

### I. Deterministic Simulation (NON-NEGOTIABLE)

- All game rules (crane, drop, landing, tiers, scoring, combo, sway, lean, stabilizer,
  strikes, roof, Quick Play, city placement/bonus rules) MUST live in `packages/sim`.
- `packages/sim` MUST be pure TypeScript with **zero runtime dependencies** (an empty
  `dependencies` field in `package.json`). It MUST run unmodified in browsers and in Node.
- Every value in simulation state MUST satisfy `Number.isSafeInteger`. Every division MUST be
  truncated (`Math.trunc` or `>>> 0`). Floats MUST NOT be stored in state.
- The simulation MUST advance only in whole fixed ticks at 60 ticks per second.
- Player inputs MUST be recorded as the tick number on which they were applied
  (`{ tick, type }`), never as wall-clock timestamps. Paused time MUST NOT advance ticks.
- The following are FORBIDDEN anywhere in `packages/sim/src`: `Math.random`, `Math.sin`,
  `Math.cos`, `Math.tan`, `Math.atan2`, `Math.pow`, `Math.exp`, `Math.log`, `Math.sqrt`,
  the `**` operator on non-literal operands, `Date`, `performance`, `setTimeout`,
  `setInterval`, `requestAnimationFrame`, and any other timer or I/O API. `Math.imul`,
  `Math.trunc`, `Math.abs`, `Math.min`, `Math.max`, and `Math.sign` are permitted.
- Trigonometry MUST use the committed, precomputed 4096-entry Q15 `SIN_LUT`
  (`packages/sim/src/sinLut.ts`, generated by `scripts/gen-sin-lut.ts`, verified by an FNV-1a
  checksum test). Randomness MUST come only from the seeded mulberry32 PRNG.
- These bans MUST be enforced by an ESLint rule (`no-restricted-properties` /
  `no-restricted-globals`) scoped to `packages/sim` **and** by an independent CI check.
  Either one failing fails the build.
- Replaying `(config, seed, inputLog)` MUST produce an identical `hashState` result in Node,
  Chromium, WebKit, and Firefox.

**Rationale**: Determinism enables replays, golden tests, and server-side score validation in
v1.1. A single float or wall-clock read breaks cross-platform replay without any visible
symptom, so the rules are absolute and enforced by machines, not by review alone.

### II. Simulation Is Authoritative; Rendering Is Presentation

- The standing tower MUST NOT be simulated with rigid bodies. Tower sway MUST be the
  deterministic horizontal-shear model of PRD §4 (`displayX[i] = restX[i] + trunc(S × i / N)`).
- Phaser 4 MUST only read and interpolate simulation state. Rendering code MUST NOT write to
  simulation state or call anything that mutates it except the public input API
  (`requestDrop`, `requestRoof`) and `step()`, driven by the fixed-timestep accumulator.
- Interpolated values (with `alpha = accumulator / TICK_MS`) are render-only and MUST NOT feed
  back into the simulation.
- Matter.js MAY be used ONLY for visual effects (missed-block slide-off, game-over collapse,
  debris). Its output MUST never reach the simulation. It MAY use non-deterministic APIs.
- Visual tilt is presentation-only and MUST NOT affect landing checks.
- Floors below the viewport MUST be culled from rendering only. They MUST remain in
  simulation state.
- Render frame rate MUST NOT affect outcomes. Driving the loop at 30/60/120/144 Hz with the
  same input ticks MUST produce identical input logs and final hashes.

**Rationale**: One authoritative model keeps gameplay fair and replayable. Anything the player
sees that is not derived from the sim is decoration, and it must not change results.

### III. Strict UI / Engine Separation

- Vue 3 (Composition API) MUST own all DOM UI: menus, HUD, city grid, dialogs, settings.
- Phaser MUST own only the game canvas. Phaser MUST be mounted in exactly one Vue component
  (`GameCanvas.vue`), created on mount and destroyed on unmount.
- Vue code MUST NOT import Phaser scenes/objects, and Phaser code MUST NOT import Vue
  components or Pinia stores. The two layers MUST communicate only through a typed event bus:
  Phaser emits simulation events; Vue sends commands (`startRun`, `pause`, `resume`,
  `placeRoof`, `quit`, `settingsChanged`).
- Pinia stores MUST contain only plain, serializable values (primitives, plain objects and
  arrays). Phaser objects, scenes, games, and simulation instances MUST NEVER be stored in
  reactive state. This MUST be verified by a unit test that inspects store state.

**Rationale**: Vue reactive proxies wrapped around engine objects degrade performance and blur
ownership. A typed bus keeps each layer testable and replaceable.

### IV. Test-First Core Logic

- Every simulation rule, tuning cap, tier boundary, scoring formula, and city rule MUST be
  covered by Vitest unit tests written before or together with the implementation.
- `packages/sim` line coverage MUST be ≥ 90%, enforced in CI.
- At least 3 committed golden replay fixtures (config + input log → score + hash), covering
  Completed, Early-roof, and Game-over runs, MUST pass in Node and in Chromium, WebKit, and
  Firefox via Playwright.
- An integer-safety fuzz test (random input logs across all tower types and Quick Play) MUST
  confirm every state value stays a safe integer and no exception is thrown.
- A change to game logic without matching tests is incomplete and MUST NOT be merged.

**Rationale**: The game's correctness lives in exact integer formulas and boundaries. Only
tests catch an off-by-one at `|d| = 50` or a silent determinism drift.

### V. Single Source of Tuning

- Every gameplay number (PRD §7.1, §7.2, and any new one) MUST live in
  `packages/sim/src/tuning.ts`, exported together with a `TUNING_VERSION` string.
- Gameplay numeric literals MUST NOT appear anywhere else in `packages/sim` or `apps/web`.
  Trivial constants (0, 1, −1, array indices, the 1000‰ unit, bit shifts defined by the PRD
  formulas) and pure render/UI styling values are exempt. Render values that mirror gameplay
  (block visual height, tilt cap, camera clearance) MUST come from `tuning.ts`.
- Any change to a tuning value MUST bump `TUNING_VERSION` and regenerate every golden fixture
  in the same change.
- Development-only runtime overrides (the PRD Phase 1 dev tuning panel) MAY inject modified
  values. Such runs MUST NOT be committed as golden fixtures or saved as city towers.

**Rationale**: Tuning is iterated heavily in Phase 2. One versioned file makes every balance
change auditable and keeps replays tied to the rules they were played under.

### VI. Performance Budgets

- Gameplay MUST sustain 60 fps on a mid-range Android phone (Pixel 6a / Galaxy A54 class,
  Chrome) and on an iPhone 12 (Safari). Measurement: a 60-floor Luxury run averages ≥ 58 fps
  with no frame above 33 ms over a 60-second capture.
- On 120 Hz displays, rendering MUST run at the display rate (≥ 110 fps average) while the
  simulation stays at 60 ticks per second. Catch-up MUST be capped at `MAX_TICKS_PER_FRAME`.
- The MVP initial download MUST be ≤ 5 MB compressed.
- The render loop MUST NOT allocate per frame (no new objects, arrays, closures, or sprites
  in hot paths). Objects and sprites SHOULD be pooled and reused.
- Performance criteria MUST be re-verified whenever a phase adds a layer (Vue shell, final art).

**Rationale**: A one-button timing game is unplayable if frames stutter. GC pauses from
per-frame allocation are the most common cause on mobile.

### VII. Accessibility and Player Respect

- Tower types MUST NEVER be distinguished by color alone. Each type MUST have a distinct
  silhouette, icon, and text label, verified by a grayscale screenshot check.
- Reduced Motion (default: the OS `prefers-reduced-motion` value) MUST disable cosmetic motion
  (screen shake, background parallax, camera bob). Tower sway MUST ALWAYS be rendered
  accurately, because it is gameplay.
- All menus MUST be keyboard-navigable with visible focus states. Gameplay MUST be playable
  with one input (pointer or Spacebar).
- Text MUST meet WCAG AA contrast.
- UI strings MUST be externalized (no hardcoded user-facing text in components).
- Production MVP builds MUST collect no analytics, set no cookies, and store no personal data.
  `localStorage` holds game data only. Phase 2 playtest telemetry is allowed only in
  development builds, stored locally, exported manually, and never transmitted.

**Rationale**: Players with color vision deficiency or motion sensitivity must be able to play
fully. A free portfolio game has no reason to track anyone.

### VIII. Phased Delivery and Simplicity

- Work MUST follow the PRD §12 phase order. A phase is complete only when all of its
  acceptance criteria pass. A later phase MUST NOT start until the previous one is complete
  (including the Phase 2 tuning gate).
- Later-phase technology MUST NOT be scaffolded early: no Vue/Pinia before Phase 3, no
  NestJS/PostgreSQL (and no `apps/api` workspace) before Phase 6, no Capacitor before Phase 7.
- Solutions SHOULD be the simplest that meets the spec (YAGNI). Speculative abstractions,
  config options, and extension points not required by the current phase MUST NOT be added.
- Every new runtime or build dependency MUST have a written justification in the plan (why it
  is needed, bundle-size cost, alternatives considered). Dependencies named in the PRD stack
  (§8.1) count as justified for their phase.

**Rationale**: Phases are ordered so the core loop is proven fun and deterministic before
anything is built on top. Early scaffolding creates maintenance cost for code that may change.

### IX. Code Standards

- TypeScript MUST use `strict` mode in every package. `any` MUST NOT be used without an
  inline comment justifying it.
- ESLint and Prettier MUST be enforced in CI. Lint or format failures fail the build.
- The repository MUST be a pnpm workspaces monorepo: `packages/sim`, `apps/web`, `apps/api`
  (from Phase 6), and `scripts/` for build scripts.
- Every exported simulation function and type, and the render/game loop, MUST have TSDoc that
  states units (su, ticks, ‰) for every numeric parameter, field, and return value.
- Animation MUST use programmatic Phaser tweens plus texture atlases. Skeletal animation
  frameworks (e.g. Spine) MUST NOT be used.

**Rationale**: Strict types and documented units prevent the most common bugs in fixed-point
code: mixing ‰ with su, or ticks with milliseconds.

## Technology and Platform Constraints

- **Stack (PRD §8.1)**: TypeScript (strict), Phaser 4 (WebGL with Canvas fallback), Matter.js
  (visual only), Vue 3 + Vite + Pinia (from Phase 3), typed event bus (`mitt`), Vitest,
  Playwright, NestJS + PostgreSQL (Phase 6), Capacitor (Phase 7).
- **Browsers**: last 2 versions of Chrome, Edge, and Firefox; Safari / iOS Safari 16+.
- **Layout**: portrait, logical resolution 720×1280, scaled to fit. Landscape on mobile shows a
  rotate overlay and pauses the game.
- **Lifecycle**: the simulation MUST auto-pause on `visibilitychange` (hidden) and on app
  backgrounding.
- **Persistence**: local save uses a versioned schema from day one, with a `migrate()`
  function and corrupted-save recovery (PRD §8.6). Saves MUST record `tuningVersion` and
  `simVersion`.
- **Server (v1.1)**: the server MUST validate runs by calling `replay()` from the same
  `packages/sim` version as the client. It MUST NOT reimplement game rules.

## Development Workflow and Quality Gates

- Every feature goes through spec → plan → tasks. Each plan MUST include a Constitution Check
  that lists Principles I–IX and states compliance or a justified, approved exception.
- CI MUST run, on every change: typecheck, ESLint, Prettier check, the forbidden-API check on
  `packages/sim`, a zero-runtime-dependency check on `packages/sim`, Vitest with the coverage
  threshold, and golden replays in Node.
- Cross-browser golden replays (Chromium, WebKit, Firefox via Playwright) MUST pass before a
  phase is marked complete and before any change to `packages/sim` is merged.
- Performance budgets (Principle VI) MUST be measured on the reference devices at the end of
  every phase that affects rendering.
- Code review MUST reject: game logic outside `packages/sim`, gameplay magic numbers outside
  `tuning.ts`, logic changes without tests, tuning changes without a `TUNING_VERSION` bump and
  regenerated fixtures, and engine objects in reactive state.

## Governance

1. This constitution overrides conflicting guidance in specs, plans, and tasks. Work that
   violates it is incomplete until fixed or covered by an approved amendment.
2. `docs/PRD.md` defines *what* is built. This constitution defines *how*. A conflict between
   them MUST be raised explicitly (in the spec, plan, or an issue) and resolved by amending one
   of the two documents. It MUST NOT be silently resolved in code.
3. Amendments require: a semantic version bump, a dated change note, and a review of existing
   specs, plans, and tasks for compliance, with any non-compliant items listed for follow-up.
4. Versioning policy:
   - **MAJOR**: a principle is removed or redefined in a backward-incompatible way.
   - **MINOR**: a principle or section is added, or guidance is materially expanded.
   - **PATCH**: clarifications, wording, or typo fixes with no change in meaning.
5. Compliance review: every plan's Constitution Check and every code review MUST verify
   compliance. Exceptions MUST be written down with a rationale and a removal condition.
